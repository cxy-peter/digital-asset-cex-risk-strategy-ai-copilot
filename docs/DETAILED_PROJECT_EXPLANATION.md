# 代码、算法与产品深挖

## 1. 为什么使用多Agent

不是让多个LLM自由聊天，而是按风控职责拆分：场景、特征、图谱、模型、用户评分、策略、回测、处置和治理分别输出结构化结果。确定性代码负责指标和状态，LLM只作为可选解释层。

## 2. 为什么使用MCP式工具层

将事件、特征、图谱、回测、治理和CMS/STR能力封装为Schema明确的工具，使Agent只能访问被授权的能力；新增工具不需要修改所有Agent Prompt。

## 3. 特征时点与防泄漏

每个特征声明`available_at`和freshness。训练样本必须满足标签在训练截止前成熟；Development用于选择，OOT不得反向参与阈值调整。用户风险等级、人工覆盖和STR结果不能被错误地当作前置特征。

## 4. 模型与规则

- Logistic：稳定、可校准的基线；
- 深度4决策树：提取可解释规则；
- XGBoost：捕捉非线性和交互；
- Risk Graph：强关系和团伙条件；
- 最终策略：规则、模型分和图谱证据的组合，而不是直接输出黑盒概率。

## 5. 策略评价

除Precision/Recall/F1外，同时考虑FPR、告警率、审核容量、风险金额捕获、PSI和业务指标波动。离线分数高不等于上线有效，必须经过simulation和效果工单。

## 6. 三层策略标签

一级标签表示风险域，二级标签表示风险场景，三级标签表示处置/运营路径。标签与策略版本和Payload Hash绑定，修改标签也形成审计记录。

## 7. Ticket Module

`StrategyEffectivenessTicket`记录策略版本、数据快照、观察窗口、效果标签、证据、建议和标注人。它将“策略上线后到底有没有用”从口头结论变成结构化运营数据。

## 8. CMS/STR联动

系统只预填内部候选案件：策略表达式、命中事件、特征快照、风险历史、图谱路径和审核状态。外部报送关闭，最终STR决策属于人工合规流程。

## 9. 为什么不放KEP和Anti-Fraud指标

KEP是监管邮件核查自动化，属于另一条实习项目；Anti-Fraud指标是案件运营数据产品。将它们拆开后，Risk Strategy项目的产品边界更清晰，也更接近真实组织中的系统拆分。
